# Несколько агентов и сессий

## Основной агент — оркестратор

Основной агент (сессия, которая говорит с владельцем) сам работу не выполняет, а оркестрирует: всю работу отдаёт подагентам через Agent. Это код, тесты, правки документации и правил, исследование и обход кодовой базы, git-операции над репозиторием (коммиты, ветки, worktree, пуш), открытие и починка PR, разбор упавшего CI, временное playtest-логирование и разбор `factorio-current.log`.

За основным агентом остаётся:

- диалог с владельцем: вопросы, брейнсторм, согласование дизайна, передача playtest-чеклиста;
- декомпозиция и раздача задач подагентам;
- проверка результатов подагентов до слов «готово» владельцу: отчёт подагента владельцу не виден, его пересказывает основной агент, и пересказывает проверив, а не вслепую;
- привязка PR к монитору приложения (`ccd_pr`) и отчёт об остатке лимитов — только у основного агента: события приходят в его сессию; починку по событию (упавший CI, конфликт, ответ на ревью) он отдаёт подагенту, а не делает сам;
- самостоятельный merge PR в ветку фазы (`github-workflow.md`, «Самостоятельный merge»): проверка чек-листа, запуск независимого ревью отдельным подагентом, сам вызов `gh pr merge` и строка о нём в отчёте владельцу; закрытие issue, карточки, обновление остальных PR и уборку — подагенту `github-ops` / `cleanup`;
- отчёты владельцу и запись в личную память.

Подагенты, которые пишут в репозиторий, работают каждый в своём git worktree (`isolation: "worktree"` у Agent); независимые задачи запускаются параллельно, как описано ниже.

Исключения два: мелкое чтение только для маршрутизации (глянуть статус, чтобы решить, кому поручить) и самостоятельный merge — чтение PR для чек-листа и одна команда merge. Правка, даже однострочная, исключением не считается.

Зачем: беречь контекст основного агента для работы с владельцем и не тратить его и лимиты плана на исполнение.

### Переиспользование подагентов

Работу, которая продолжает дело уже отработавшего подагента, отдавать ему же, а не запускать нового.

- Продолжение — возобновить через `SendMessage` по его agentId: правки после ревью, следующий шаг той же задачи, доработка того же PR, починка по итогам playtest в его области. У него уже есть контекст, а возобновление дешевле нового запуска.
- Новый подагент — когда задача независима от прошлой; когда нужен свежий взгляд (независимое ревью); когда контекст прошлого разросся; когда прошлый занят.
- Основной агент ведёт у себя перечень «agentId → тема, ветка/PR, модель», чтобы знать, кого продолжать; `ListAgents` — для сверки.
- Сообщение возобновляемому подагенту самодостаточное: полная постановка нового шага, а не «продолжай». В нём повторяются ограничения: свой worktree, реплики в GitHub — с «🤖», монитор PR и отчёт о лимитах — не его. Исполнителю и автору плана — ещё и требование о фиксации трудностей.
- Возобновлённый подагент, как и новый, по завершении убирает за собой worktree; если продолжение ждёт ещё шаг в той же ветке, основной агент говорит об этом в сообщении.

## Выбор модели подагента

Перед запуском подагента — чек-лист из начала `usage-reports.md`.

- **Сложные** — на Fable 5.1 (`model: "fable"`; у неё свой недельный лимит): архитектурные развилки и проектирование (брейнсторм, план фазы, ADR), нетривиальная отладка и поиск причины (в том числе по логу playtest), независимое ревью, крупные рефакторинги через несколько модулей, работа с проводами и `entity_number` (ADR-0001, раздел 6).
- **Обычные** — на модели по умолчанию (Sonnet 5.5): исполнение готового плана по шагам, правки правил и документации, мелкие правки, playtest-логирование.
- **Механические** — уборка после merge, статусы PR и CI, issue и карточки — подагентам `cleanup` и `github-ops` (модель Haiku, урезанный набор инструментов).
- Opus 5.5 — для сложных задач, когда лимит Fable исчерпан или близок, и по умолчанию у `reviewer`.
- Возобновление через `SendMessage` модель не меняет: продолжать сложную работу — у подагента на Fable; если продолжение обычное, а прошлый был на Fable, часто дешевле новый подагент на обычной модели.
- Перед сложной задачей смотреть окно «Weekly · Fable» по `usage-reports.md`. Прогноз выше 80% — на Fable только самое нужное; выше 100% — Fable не запускать и сказать владельцу прямо. Исчерпание лимита Fable работу не останавливает: продолжать на другой модели и сообщить об этом.
- Названия моделей в поле проекта «Модель» и таблицах затрат — полные: Sonnet 5.5, Fable 5.1, Opus 5.5, Haiku 5.5.

## Типы подагентов и короткая постановка

`general-purpose` — только когда ни один тип не подходит: он несёт полный набор схем инструментов на каждом ходе. Типы в `.claude/agents/` (модель — по умолчанию типа, `model` у Agent её переопределяет):

| Тип | Для чего | Модель |
| --- | --- | --- |
| `code-executor` | исполнитель задачи по плану: Lua-код, busted-тесты (TDD), playtest-логирование, PR | Sonnet 5.5; сложное — Fable 5.1 / Opus 5.5 |
| `doc-writer` | план фазы, ADR, `phase-N-implementation.md`, roadmap, CHANGELOG, правила, тексты issue | Sonnet 5.5; план и ADR — Fable 5.1 / Opus 5.5 |
| `reviewer` | независимое ревью diff (условие 5 «Самостоятельного merge») | Opus 5.5 / Fable 5.1 |
| `github-ops` | PR-обвязка, issue, метки, milestone, карточки, статусы, лог CI, учёт затрат | Haiku 5.5 |
| `cleanup` | ветки и worktree после merge | Haiku 5.5 |
| `Explore` (встроенный) | обзор кода только чтением | по умолчанию |

Постановка — только дельта; шаблон работы (worktree, ветка, проверки, PR, маркер «🤖», трейлер, трудности, отчёт) зашит в тип и не повторяется: «Issue #N, база `phase/N-<slug>`, ветка `<ветка>`. Раздел плана `docs/phases/phase-N-plan.md` «Задача K». Метка `группа/…`; модель для поля «Модель» карточки issue ставит `github-ops` (`github-workflow.md`, «Метки»). Особенности: …». Подагент не возвращает логи, диффы и тексты документов — только итог по формату типа. Разделы больших файлов — `node .claude/scripts/md-section.mjs`.

Цифры затрат подагента — из его транскрипта, не из отчёта: основной агент записывает `agentId` каждого запуска и после этапа вызывает `node .claude/scripts/cost-report.mjs add <issue> --stage … --agents <id,…>` (или поручает `github-ops`).

## Трудности исполнителей

Исполнитель и автор плана фиксируют реальные трудности комментарием к issue работы (`gh issue comment <N> --body-file <файл>`, первая строка с «🤖»). Если issue нет — трудности идут в итоговый отчёт основному агенту тем же форматом. При закрытии фазы основной агент переносит их суть в раздел «Решения, принятые по ходу» или «Найденные API-факты» `phase-N-implementation.md`.

Формат — ровно три блока, не более 4 предложений в каждом:

```
🤖 **Трудность: <коротко, одной строкой>** (этап: plan|exec|ci-fix|playtest)
- **Проблема:** что именно не получалось или сломалось.
- **Причина:** почему так вышло: установленная, не догадка; если не установлена — так и написать.
- **Решение:** что сделал и чем проверил (хэш коммита или PR).
```

- Одна трудность — один комментарий, в issue, а не в PR.
- Писать то, что отняло заметное время, потребовало отступления от плана или может повториться: расхождение плана с кодом, неочевидное поведение Factorio API (особенно расхождение документации `/latest/` и установленной версии), нестабильный тест, находка ревью, потребовавшая переработки.
- Не писать рутину: обычную правку по ревью, опечатки, ожидаемые шаги плана.
- В итоговом отчёте исполнитель указывает число таких комментариев и ссылки на них. Основной агент включает этот блок в каждую постановку исполнителю и автору плана и проверяет по отчёту, что трудности зафиксированы.

## Параллельное исполнение плана

Независимые задачи плана запускаются параллельно, а не строго по одной.

Параллельно — только задачи без общих файлов и без зависимости по интерфейсам (по графу зависимостей плана). В этом моде модулей мало, и многие задачи правят один и тот же файл (`scripts/canvas.lua`, `scripts/input.lua`, `control.lua`) — такие задачи остаются последовательными. Каждый исполнитель — в своём worktree (`isolation: "worktree"`).

Число параллельных исполнителей ограничивается прогнозом лимитов по `usage-reports.md`.

## Playtest

Ручной playtest проводит владелец — подагенты игру не запускают. Порядок — `docs/sdlc.md`, «Тестирование»: исполнитель (`code-executor`) добавляет временное логирование с префиксом `eb playtest:` отдельным коммитом в ветке фазы; основной агент передаёт владельцу чеклист; лог `factorio-current.log` разбирает подагент (Fable 5.1 для нетривиальной причины); после подтверждения логирование убирается отдельным PR перед финальным PR фазы.

## Координация других сессий

Когда владелец поручает координировать другие сессии Claude Code (`ListAgents`, `SendMessage`) и идти по плану, распределение задач — на координаторе: освободившейся сессии сразу даётся следующий пункт. Не просить владельца открыть новую сессию или выбрать исполнителя. Событие по PR обрабатывает только сессия-владелец PR (`github-workflow.md`, «Пока PR ждут ревью»). К владельцу идут только его решения: архитектурные развилки, merge в `main`, playtest, действия, запрещённые правами сессий.
