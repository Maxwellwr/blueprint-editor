# GitHub: PR, ревью, CI, ветки, задачи

Репозиторий — `github.com/Maxwellwr/blueprint-editor`, CI — GitHub Actions (`.github/workflows/test.yml`). Инструмент — `gh`. Процесс перенесён из barista-free (там Gitea) и переложен на GitHub; где поведение GitHub отличается, это сказано явно.

Отдельного бота нет: всё, что агенты пишут в GitHub (PR, issue, комментарии, ответы в ревью), идёт от аккаунта владельца, под которым залогинен `gh`. Чтобы реплики агента отличались от реплик владельца, **комментарии и ответы агента начинаются с «🤖»**. Тела PR и issue, созданных агентом, маркер не требуют: автор PR — всегда агент по поручению владельца.

## PR и `main`

- В `main` — только через PR: ветка → `gh pr create` → merge после зелёной проверки `test`. Прямой пуш и force-push в `main` запрещает ruleset репозитория (настройка — раздел «Первичная настройка репозитория»).
- Git-хуки (`pre-push` и т. п.) для этого не предлагать — серверного запрета достаточно.
- Merge в `main` делает владелец. PR в ветку фазы, где решение владельца не нужно, мёржит основной агент сам (раздел «Самостоятельный merge»).
- GitHub не даёт одобрить собственный PR, а PR агента создаются от аккаунта владельца. Поэтому «одобрение» владельца — это merge (в `main`) или явное слово в комментарии PR или в чате, а не кнопка Approve.

## Ветка фазы и хотфиксы

Фаза из `docs/roadmap.md` — это этап. Она ведётся в ветке `phase/N-<slug>` (например, `phase/4-save`), отведённой от свежего `main`. Ветку создаёт и пушит основной агент в начале фазы. Все PR фазы — план, задачи, правки по playtest, закрытие фазы — идут в неё (`gh pr create --base phase/N-<slug>`), а в `main` она сливается одним финальным PR по окончании фазы (Definition of Done в `docs/sdlc.md`). Тег `vA.B.0` ставит владелец после merge финального PR.

- У ветки фазы нет защиты: прямой пуш в неё технически возможен, но агентам запрещён — только PR, merge — по «Самостоятельный merge». Сервер ни CI, ни способ merge там не проверяет, это делает агент по чек-листу.
- Хотфикс уже выпущенной версии — ветка от `main`, PR в `main`, патч-версия `vA.B.(C+1)` (`docs/sdlc.md`, «Версионирование»). Сразу после его merge сессия-владелец хотфикса подтягивает `main` в ветку фазы sync-PR'ом: ветка `claude/sync-main-<дата>` от `origin/phase/N-<slug>`, `git merge origin/main`, PR в ветку фазы; merge — по «Самостоятельный merge», с конфликтом по смыслу — владелец. Направление только `main` → ветка фазы; обратно — только финальный PR.
- Конфликт при подтяжке решает агент в sync-ветке, если он механический (`CHANGELOG.md`, версия в `info.json`, `CLAUDE.md`); по смыслу — вопрос владельцу в PR, подтяжку не откладывать.
- `Closes #N` закрывает issue только при merge в ветку по умолчанию (`main`). Для PR в ветку фазы агент после merge закрывает issue сам: `gh issue close <N> --comment "🤖 Сделано в <PR>, merge-коммит <sha>"`.
- После merge подтяжки открытые PR фазы обновляются из ветки фазы: `gh pr update-branch <N>` (merge базы в ветку PR, историю не переписывает).

## Спеки и планы

План фазы (`docs/phases/phase-N-plan.md`) владелец утверждает в PR в ветку фазы, а не в чате: это заменяет шаг «попросить пользователя прочитать файл» из `superpowers:brainstorming` и `superpowers:writing-plans`. Если фаза требует архитектурного решения вне плана — оно оформляется отдельным ADR (`docs/adr/`) в том же или отдельном PR.

- Закоммитил план — сразу пушить ветку и открывать PR, не спрашивая «открывать ли PR». В описании — суть и то, на что нужно решение.
- Вопросы к владельцу — нумерованным разделом плана с рекомендацией у каждого пункта. Владелец отвечает в ревью PR.
- К исполнению переходить, только когда владелец смёржил PR плана или прямо сказал, что принимает. Молчание и «вроде норм» не считаются.
- PR планов, ADR и правил основной агент не мёржит никогда (раздел «Самостоятельный merge»).

## Ответы в ревью

Владелец ревьюит PR на GitHub и задаёт вопросы там же. Отвечать — в том же треде, а не отдельным комментарием: иначе ответ отрывается от строки кода.

- Ответ в тред ревью: `gh api -X POST repos/{owner}/{repo}/pulls/<N>/comments/<comment_id>/replies -f body="🤖 …"`, где `comment_id` — последний вопрос владельца в треде (id видны в `gh api repos/{owner}/{repo}/pulls/<N>/comments`).
- Общий комментарий к PR (не к строке) — ответ обычным комментарием: `gh pr comment <N> --body "🤖 …"`.
- Вопросы, требующие решения владельца, удобно выносить в план нумерованным разделом с рекомендацией у каждого пункта.

## Задачи на GitHub

Работа ведётся задачами: milestone на фазу в формате `v{Major}.{Minor}` — по версии, которую фаза выпустит (Phase 4 → `v0.5`); issue на каждую задачу из `phase-N-plan.md`; зонтичный issue «Phase N — <название>», который закрывает `Closes` финального PR. Хотфиксам milestone не нужен. Каждый issue и PR работы добавляется в проект (доску) «Blueprint Editor».

- Тело issue: суть, критерии приёмки или ссылка на раздел плана, зависимости строкой «Блокируется: #N». В PR работы — `Closes #N` (для PR в ветку фазы закрытие делает агент, см. выше). Чек-листа статуса в теле нет — его ведёт колонка доски.
- Milestone — только у задач фазы; бэклог без milestone. Milestone фазы заводится вместе с веткой фазы: `gh api -X POST repos/{owner}/{repo}/milestones -f title=v0.5 -f description="Phase 4 — …"`.

### Метки

- Группа — обязательна, ровно одна: метка `группа/<Название>`. У GitHub нет взаимоисключающих меток, поэтому «ровно одна» держит агент: ставя новую группу, снимает прежнюю. Стартовый набор: «Холст и ввод», «Рендер», «Импорт и экспорт», «Палитра и GUI», «Провода», «Совместимость», «Процесс», «Релиз». Сначала смотреть существующие (`gh label list`), подходящей нет — создать: `gh label create "группа/<Название>" --color <rrggbb> --description "Группа: <Название>"`.
- Модель исполнителя — не метка, а поле проекта «Модель» (single select: `Sonnet 5.5`, `Fable 5.1`, `Opus 5.5`, `Haiku 5.5`). Ставится только на карточку issue (на карточку PR не ставится): при заведении issue по плану (`github-ops` / `doc-writer`); если задачу фактически исполнила другая модель, `github-ops` исправляет поле по постановке основного агента после этапа. Команда: `gh project item-edit --id <id карточки> --project-id <id проекта> --field-id <id поля «Модель»> --single-select-option-id <id варианта>` (id — из `gh project field-list`, не хардкодить).
- `документация` — для задач про документацию.
- `playtest` — задача меняет поведение, которое проверяется только в игре (код с Factorio API): её пункт попадает в playtest-чеклист фазы.
- `блокер` — блокировка как свойство карточки в любой колонке: упал CI, ждём зависимость или ответ владельца. Ставить при блокировке, снимать при снятии.
- Статус метками не ведём: его говорит колонка доски.

### Колонки доски

Доска — GitHub Project (v2) владельца «Blueprint Editor», поле `Status` с вариантами слева направо: Backlog → Spec → Spec Review → To Do → In Progress → Review → Done. Чем правее, тем больше вложено ресурса и тем ценнее карточка.

- Backlog — заведён.
- Spec — пишется план или ADR.
- Spec Review — PR плана ждёт ревью владельца.
- To Do — план принят, исполнитель не запущен.
- In Progress — исполнитель работает.
- Review — PR исполнителя ждёт ревью владельца или самостоятельного merge.
- Done — смёржено.

Работа с доской требует scope `project` у `gh` (`gh auth refresh -s project`, один раз). Добавить карточку — `gh project item-add <номер проекта> --owner Maxwellwr --url <ссылка на issue или PR>`. Перенести — `gh project item-edit --id <id карточки> --project-id <id проекта> --field-id <id поля Status> --single-select-option-id <id варианта>`. Id проекта, поля и вариантов не хардкодить: `gh project list --owner Maxwellwr`, `gh project field-list <номер> --owner Maxwellwr --format json`, `gh project item-list <номер> --owner Maxwellwr --format json`.

**Автоперемещение в Done у GitHub есть** (в отличие от Gitea в barista-free): встроенные workflows проекта «Item closed» и «Pull request merged» ставят `Status = Done`. Их включает владелец в настройках проекта (Workflows). Поэтому после merge PR в `main` карточки двигать не нужно. После merge PR в ветку фазы карточка PR уйдёт в Done сама, а карточка issue — когда агент закроет issue. Перед ручным переносом проверить, не сделал ли это workflow.

Порядок в Backlog — очередь взятия: берётся верхняя карточка. Новую вставлять по ценности и стоимости, а не в конец: сначала задачи текущей фазы, затем корректность и гигиена, затем следующие фазы по `docs/roadmap.md`.

Трудности исполнителей фиксируются комментарием в issue работы — формат в `agent-orchestration.md`, раздел «Трудности исполнителей».

### Учёт затрат в задаче

По каждому этапу работы (план, исполнитель, правка по ревью, разбор CI) записывать токены и время по ходу, а не задним числом.

- Запись этапа — одной командой: `node .claude/scripts/cost-report.mjs add <issue> --stage <код> --agents <agentId,...> [--pr N] [--label "<строка таблицы>"] [--since ISO] [--until ISO]` (`--dry-run` — показать). Скрипт считает по транскриптам подагентов и правит комментарий учёта в issue (новый — только если его нет). Учёта времени, как в Gitea, у GitHub нет: минуты живут в таблице комментария и в поле проекта «Минуты».
- Комментарий учёта — детализация по этапам, поля проекта — итоги по issue. Итоги (`totals`: минуты, ходы, вызовы инструментов, input, output, cache write, cache read, взвешенные токены) скрипт после `add` и `rewrite` сам пишет в числовые поля карточки issue: «Минуты», «Ходы», «Вызовы инстр.», «Input», «Output», «Cache write», «Cache read», «Взвеш. токены». Поле «Модель» скрипт не трогает (см. «Метки»). Числовые поля вручную не править; пересинхронизировать из комментария — `node .claude/scripts/cost-report.mjs sync <issue>`. Проект — `--project N` или env `COST_PROJECT` (по умолчанию 2); нет карточки — предупреждение, не ошибка. Суммы числовых полей в группировке доски по milestone дают стоимость фазы.
- Один комментарий учёта на задачу: таблица «этап / модель / минуты / ходы / вызовы инструментов / input / output / cache write / cache read / взвешенные / финальный контекст» и сноска об источнике. В конце — скрытый блок `<!-- cost-report:v2 {…} -->` (GitHub его не показывает); комментарий узнаётся по этому блоку, а не по автору.
- `weightedTokens` — оценка в эквиваленте входных токенов по соотношению цен API: `input + 1,25 × cache write + 0,1 × cache read + 5 × output`; ориентир для сравнения этапов, а не процент недельного окна.
- Источник цифр — транскрипты подагентов (`~/.claude/projects/<проект>/<сессия>/subagents/agent-<id>.jsonl`), а не `subagent_tokens` из отчёта: тот — размер контекста последнего вызова и занижает расход в десятки раз (замер barista-free 18.10.2026). Возобновлённый подагент дописывает тот же транскрипт: этап продолжения — с окном `--since`/`--until`.
- Не входят: время ревью и playtest владельца, ожидание оркестратора. Подагентов уборки и разовые правки вне задач в issue не вносить.

## Пока PR ждут ревью

За открытыми PR следит десктопное приложение Claude, а не скрипт: сразу после `gh pr create` основной агент вызывает `get_status` из инструментов `ccd_pr` и, если PR там не виден, привязывает его `bind_pr`; затем смотрит CI и предлагает владельцу Auto-fix. Приложение само будит сессию при падении CI, конфликте и комментариях ревью. `CronCreate`, `ScheduleWakeup`, `/loop`, `Monitor` и ручной опрос `gh pr checks` для слежения не использовать.

- Упавшая джоба или конфликт сразу уходят в починку — подагенту-автору PR (`SendMessage`) или новому исполнителю.
- После каждого merge в ветку фазы остальные открытые PR фазы проверяются на конфликт и обновляются: `gh pr update-branch <N>`. При конфликте ничего не разрешать самому — отдать исполнителю PR или владельцу.
- Перезапуск упавшей джобы (`gh run rerun <run-id> --failed`) имеет смысл, только если код и окружение не менялись (единичный сбой раннера).
- Зелёный CI на PR в ветку фазы — сигнал пройти чек-лист «Самостоятельный merge», а не ждать владельца.

**Несколько сессий.** Событие по PR обрабатывает только сессия-владелец этого PR (открыла или ведёт его). Перед ответом в ревью и перед починкой сверять по `gh pr view <N> --comments`: не ответил ли уже агент (реплика с «🤖») и не появился ли новый коммит в ветке PR. Соседние сессии видны через `ListAgents` и `mcp__ccd_session_mgmt__list_sessions`.

## Самостоятельный merge

Где решение владельца не нужно, PR мёржит основной агент сам, не дожидаясь владельца; владелец узнаёт из отчёта.

**Куда.** Только PR в ветку фазы `phase/N-<slug>`: задачи фазы и sync-PR подтяжки `main`. PR в `main` (хотфиксы, финальный PR фазы, правила вне фазы) мёржит только владелец.

**Условия — все вместе:**

1. CI на head-коммите зелёный целиком: `gh pr checks <N>` — проверка `test` в `pass`, ни одной в `pending` или `fail`. Ветка фазы без защиты, сервер merge с красным CI не остановит — это главная проверка.
2. Конфликтов нет: `gh pr view <N> --json mergeable` — `MERGEABLE`. Ветка отстала — `gh pr update-branch <N>`, новый CI и чек-лист заново.
3. Заголовок без `WIP:` и PR не черновик; на комментарии и ревью владельца есть ответ и исполнение; в описании PR нет открытых вопросов к владельцу.
4. По сути решения владельца не нужно (список ниже).
5. PR с кодом (что-то кроме `docs/**`, `*.md`, `.claude/**`) прошёл независимое ревью: подагент `reviewer` на Opus 5.5 или Fable 5.1, не автор PR, по diff ветки, без подсказки ожидаемого вердикта. Подтверждённые находки — merge нет, PR к исполнителю, после правок — ревью заново. PR без кода — без ревью.

**Решение владельца нужно, если PR:**

- расходится с планом фазы не механически, или исполнитель сам пометил пункт как требующий решения;
- меняет план фазы или ADR по смыслу (отметка о выполнении — не смысл);
- несёт миграцию `storage`, которая удаляет или преобразует данные (добавляющая nil-safe поле — можно, `docs/sdlc.md`, «Архитектурные принципы»);
- меняет `info.json` сверх версии: зависимости, `factorio_version`, имя мода;
- трогает `.github/workflows/`, `.claude/rules/`, `.claude/agents/`, `.claude/settings.json`, `docs/sdlc.md` или «Договорённости» в `CLAUDE.md` (механическая подтяжка в sync-PR — можно);
- добавляет внешнюю зависимость (библиотеку Lua, мод в `dependencies`, сторонний action в CI) или меняет лицензию;
- отступает от архитектурного принципа из `docs/sdlc.md` (хардкод имён прототипов, прямой доступ к `storage` в обход `state.lua` и т. п.).

**Не мёржит никогда:** PR в `main`, в том числе финальный PR фазы; PR с красным, неполным или устаревшим CI; PR с неотвеченными вопросами владельца; PR планов, ADR и правил; PR в чужие репозитории. Теги, релизы и публикацию на mod portal — тоже только владелец.

**Как.** `gh pr merge <N> --squash --match-head-commit <sha с зелёным CI> --delete-branch`; `--match-head-commit` — всегда: GitHub откажет, если head сдвинулся после проверки. Способ:

- `--squash` — по умолчанию: одна задача — один коммит в ветке фазы, заголовок — Conventional Commit из заголовка PR;
- `--rebase` — в PR несколько осмысленных коммитов, которые полезно сохранить по отдельности.

Финальный PR фазы в `main` владелец мёржит способом «Rebase and merge» или «Create a merge commit» — история задач фазы при этом сохраняется.

**После.** Агент закрывает issue комментарием со ссылкой на merge-коммит и PR, проверяет, что карточки ушли в Done (иначе переносит), обновляет остальные открытые PR фазы (`gh pr update-branch`); локальные ветки и worktree убирает подагент `cleanup`. Затем проверить прогон пуша в ветку фазы (`gh run list --branch phase/N-<slug> --limit 1`): упал — починка раньше следующего merge. Владельцу — одна строка в ближайшем отчёте: «смёржил #N в phase/N-…: что; CI зелёный на `<sha>`; способ и почему; ревью — модель и итог или „без кода“».

## После merge

Убирать за собой ветки и worktree. Удалённую ветку удаляет `--delete-branch` при merge (или автоудаление веток в настройках репозитория); на агенте — локальные ветки, worktree и `git fetch --prune`.

Удалять только законченное: PR смёржен или закрыт — проверять по `gh pr view <N> --json state,mergedAt,headRefOid`, а не по `git merge-base` (squash-merge git влитым не считает). Не трогать ветки открытых PR, чужие рабочие ветки и worktree, worktree с незакоммиченными изменениями или неотправленными коммитами.

`git branch -D` локальной ветки агент делает без вопроса владельцу, если выполнены оба условия: (а) PR этой ветки смёржен (`state: MERGED`); (б) на ветке нет коммитов, которых нет на сервере: `git merge-base --is-ancestor <ветка> origin/<база>` истинно либо tip ветки совпадает с `headRefOid` смёрженного PR. Не выполнено хоть одно — не удалять. Ветки закрытых без merge PR — только по слову владельца; `main`, `phase/*`, ветки открытых PR и чужие рабочие ветки не удалять никогда.

Служебные ветки `worktree-agent-<id>` (их создаёт харнесс для worktree подагентов) удаляются без вопроса, если: (а) ветка не чекаутнута ни в одном worktree (`git worktree list`); (б) её tip входит в `origin/main` или `origin/phase/*` либо совпадает с `headRefOid` смёрженного PR; (в) уникальных неотправленных коммитов нет. Есть такие коммиты — не удалять, сообщить владельцу.

## Первичная настройка репозитория

Делает владелец один раз (или агент по его прямому слову — это действия во внешнем сервисе):

1. Создать репозиторий и запушить `main`: `gh repo create Maxwellwr/blueprint-editor --private --source . --push` (публичность — решение владельца).
2. Ruleset для `main`: запрет прямого пуша и force-push, обязательный PR, обязательная проверка `test`. Settings → Rules → Rulesets, или `gh api -X POST repos/{owner}/{repo}/rulesets` с телом правил.
3. В настройках репозитория: включить автоудаление веток после merge, разрешить способы merge «Squash», «Rebase», «Merge commit».
4. Проект «Blueprint Editor»: `gh auth refresh -s project`, `gh project create --owner Maxwellwr --title "Blueprint Editor"`, в поле `Status` — варианты из «Колонки доски»; в Workflows проекта включить «Item closed» и «Pull request merged» → Done и «Auto-add to project» для этого репозитория.
5. Метки групп, `документация`, `playtest`, `блокер` — из раздела «Метки».
6. Поля проекта (`gh project field-create 2 --owner Maxwellwr --name … --data-type …`): «Модель» — SINGLE_SELECT с вариантами `Sonnet 5.5`, `Fable 5.1`, `Opus 5.5`, `Haiku 5.5`; NUMBER — «Минуты», «Ходы», «Вызовы инстр.», «Input», «Output», «Cache write», «Cache read», «Взвеш. токены». Если поле уже есть — не дублировать.
