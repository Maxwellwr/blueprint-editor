# Phase 1 — Read-only render of an existing blueprint — реализация

- Ветка: `phase-1-render` → `main`
- Версия после мержа: `info.json` `0.2.0`
- Дата завершения: 2026-09-06

## Что сделано

- `scripts/state.lua` — `Session` расширена аддитивно: `mode` (`"new"`/`"edit"`), `origin`, `next_internal_id`, `entities`, `tiles`, `blueprint_center`, `render_ids`, `label`, `icons`, `blueprint_snap`. Новый хелпер `M.new_render_ids()` — единая точка правды для формы `render_ids`, используется в трёх местах (`start_session`, миграция, `rendering.lua`).
- `scripts/migrations.lua` — первый реальный шаг `0.2.0`: нормализует форму `Session` для сессий, переживших Phase 0 (все новые поля — nil-safe, `x = x or default`). Мод_version после `M.run()` теперь всегда берётся из `script.active_mods["blueprint-editor"]`, а не из версии последнего применённого шага.
- `scripts/blueprint_io.lua` (новый) — `import_from_stack(cursor_stack)`: читает настроенный blueprint из курсора игрока (read-only, ничего не перекладывает), возвращает `import_data` или `nil` (тихий фолбэк в "new"-режим). Внутри — две чистые функции без Factorio API, обе покрыты `busted` по TDD:
  - `build_import_data(bp_entities, bp_tiles)` — назначает монотонный `internal_id` (не переиспользуя `entity_number`), индексирует тайлы по `"x,y"`.
  - `compute_bounding_box_center(entities, tiles)` — центр bounding box содержимого чертежа (добавлена по ходу фазы, см. ниже).
- `scripts/rendering.lua` (новый) — `draw_grid` (128×128 тайлов вокруг точки высадки игрока), `draw_entities`/`draw_tiles` (плоские иконки `entity/<name>`/`tile/<name>` с фолбэком на `utility/missing_icon`, если у игрока не установлен исходный мод), `clear_session_renders`.
- `scripts/surface.lua` — `teleport_in` принимает опциональный `import_data`; когда он есть, курсор игрока не трогается вообще (blueprint остаётся в руке нетронутым). Добавлен свободный облёт: игрок переключается на `defines.controllers.god` при входе (персонаж остаётся стоять в реальном мире) и обратно на `character` при выходе.
- `control.lua` — `on_toggle_editor` теперь оркестрирует: импорт → `teleport_in` → отрисовка (вход), очистка рендера → `teleport_out` (выход).
- `.busted`, `spec/blueprint_io_spec.lua` — первая тестовая инфраструктура в репозитории; `busted` 2.3.0 установлен на машину разработчика (WinGet + LuaRocks + MSVC-компиляция C-зависимостей `busted`, без прав администратора — Chocolatey, изначально выбранный, требовал elevation, которого не было). 8/8 тестов, зелёные.
- `.luarc.json` — дополнен глобалами `busted` (`describe`/`it`/`assert`/...) и `helpers`, диагностика `undefined-field` отключена (ложные срабатывания на `assert.*` от `luassert`).

Оба заявленных в плане пункта подтверждены playtest'ом:

- **Основной сценарий** — импорт существующего blueprint'а (захваченного вручную, не через Blueprint Library) и его read-only рендер на канвасе подтверждён дважды, на двух разных чертежах.
- **Спайк Blueprint Library** (ADR-0001 §2, §8(b).7) — **подтверждён провал**: `cursor_stack.valid_for_read` возвращает `false` для blueprint'а, перетащенного прямо из игровой Blueprint Library в курсор. Ровно тот риск, который ADR предвидел; воркэраунд «сначала перетащить в инвентарь/книгу» работает и задокументирован как известное ограничение MVP — обходного кода не написано (ADR-0001 §8(b).7 явно допускает такой исход).

## Решения, принятые по ходу (отклонения от phase-1-plan.md / ADR-0001)

Все найдены через ручной playtest, не через ревью кода до запуска игры:

1. **`LuaRenderObject`, а не числовой id.** План (и автор плана) исходил из устаревшей (Factorio 1.1-эры) формы API — `rendering.is_valid(id)`/`rendering.destroy(id)`. В Factorio 2.0 `rendering.draw_*` возвращает объект `LuaRenderObject`; валидность — свойство `object.valid`, уничтожение — метод `object:destroy()`. Подтверждено lua-api.factorio.com, исправлено без нового ADR (уточнение факта API).
2. **Свойство называется `preview_icons`, не `blueprint_icons`.** ADR-0001 §8(b).2 использует последнее имя — в текущей версии API такого свойства не существует. Найдено и исправлено ДО playtest'а (сверка с документацией перед написанием кода), а не после краша.
3. **Blueprint не «пинится» в скрытый инвентарь в Phase 1.** Сессия read-only, ничего не пишется обратно — риск потери данных, ради которого задуман pinning (ADR-0001 §8(b).3), появится только с реальным редактированием (Phase 2+). `Session.origin = { kind = "cursor" }` — вариант, уже предусмотренный в самом ADR.
4. **Свободный облёт (`defines.controllers.god`) вместо обычного персонажа.** Не было в исходном `phase-1-plan.md` — playtest показал, что персонаж застревает в декорациях отрендеренных сущностей (сами по себе они не имеют коллизии — дело в обычной физике персонажа на канвасе). Решение — тот же god-контроллер, что уже использует Blueprint Sandboxes (ADR-0001 §1, reuse-research) и что Phase 0 уже называла ожидаемым будущим шагом («станет обязательным в фазе, где вход в редактор начнёт форсировать god/spectator-контроллер»). Персонаж остаётся стоять в реальном мире на время сессии, переприкрепляется при выходе. Потребовало двух дополнительных фиксов по ходу того же playtest'а:
   - `set_controller{type=character, character=X}` требует, чтобы игрок уже был на той же поверхности, что и `X` — первая версия фикса переприкрепляла персонажа до телепортации обратно, что крашило мод; исправлено изменением порядка (сначала телепорт, потом реattach).
   - God-переключение теперь применяется, только если вход идёт из обычного character-контроллера (`pre_edit.character` не `nil`) — иначе нечего сохранять/восстанавливать.
5. **Центрирование содержимого чертежа на точке высадки игрока.** Не было в исходном плане — обнаружено на втором протестированном чертеже (первый случайно был захвачен рядом с (0,0) в реальном мире и замаскировал проблему). `BlueprintEntity.position` — координаты на момент захвата в реальном мире, не нормализованные к (0,0); чертёж, захваченный далеко от спавна, рендерился корректно (`draw_entities` создавал все render-объекты), но далеко за пределами видимой области и вне зоны, куда телепортируется игрок. Это системная проблема для любого чертежа, а не частный случай. Добавлена чистая функция `blueprint_io.compute_bounding_box_center` (TDD, 4 теста) — центр bounding box чертежа вычитается при отрисовке, `raw.position` не мутируется (preserve-unknown-fields).
6. **Финальный whole-branch review (ledger) нашёл и потребовал исправить до мержа** (5 Important + 7 в рамках фикс-волны Minor, все закрыты одним заходом): `teleport_out` мог выкинуть чужой (игрока) blueprint из курсора при выходе — теперь чистится только `eb-cursor-tool`; осиротевшая сессия (`on_player_joined_game`) не уничтожала свои render-объекты вопреки прямому требованию ADR-0001 §4 — исправлено; сущность/тайл из неустановленного у игрока мода могли уронить весь мод через невалидный sprite-path — добавлена проверка `helpers.is_valid_sprite_path` с фолбэком на `utility/missing_icon`; отсутствовало сообщение игроку при неудачном восстановлении персонажа (например, если тот погиб, пока стоял без присмотра); плюс россыпь мелких находок (дублирование формы `render_ids`, хрупкий формат ключа тайла, неиспользуемый параметр, отсутствие проверки поверхности перед `set_controller`, избыточное условие перед отрисовкой, дрейф `mod_version` после миграции, повторный резолв поверхности).

## Известные ограничения / перенесено в следующую фазу

- **Blueprint Library.** Blueprint, перетащенный прямо из игровой Blueprint Library в курсор, не читается (`cursor_stack.valid_for_read = false`) — подтверждённый playtest'ом провал ровно того риска, что называл ADR-0001 §2/§8(b).7. Воркэраунд: сначала перетащить в инвентарь или blueprint-книгу, потом брать в руку. Обходного кода в MVP нет (ADR это прямо допускает).
- **Персонаж уязвим во время сессии.** Пока игрок в god-режиме на канвасе, его персонаж стоит без присмотра в реальном мире (та же цена, что платит Blueprint Sandboxes, см. ADR-0001 §1). Если он погибнет/будет перемещён другим модом, `teleport_out` не крашит (проверка `.valid`/`surface`), но выводит игрока в god-режим без персонажа насовсем — сообщение об этом печатается, полноценного recovery-flow нет.
- **`pre_edit.controller_type` используется только частично.** God-режим применяется только при входе из обычного character-контроллера; для редких путей входа из другого контроллера (spectator/editor) поведение "restore exactly" (ADR-0001 §5) не форсирует god — игрок остаётся в своём текущем контроллере, что честнее, чем раньше, но само поле `controller_type` в `pre_edit` по-прежнему не используется для полноценного восстановления произвольного контроллера — предвиденное Phase 0 ограничение, не полностью закрытое и сейчас.
- **`EntityRecord` без `wires`.** Wire-бухгалтерия (переброс ссылок при удалении, полноценный remap с проводами) — Phase 2 по роадмапу, не в этой фазе. Поле добавится аддитивно.
- **Сетка фиксирована на 128×128 тайлов вокруг точки высадки.** Центрирование (это фаза) гарантирует, что центр содержимого чертежа совпадает с точкой высадки, но крупный blueprint всё равно может выходить за пределы визуальных линий сетки (сама отрисовка сущностей/тайлов такого ограничения не имеет — просто нет фонового ориентира за пределами ±64 тайлов).
- **`ENTITY_RENDER_WARN_THRESHOLD = 2000`** — грубая оценка, тестовые чертежи (до 82 сущностей) её не приближали; уточнить, когда реально понадобится большой blueprint.
- **Формат ключа тайла (`"x,y"` через `string.format("%d,%d", ...)`)** — корректен для целых координат тайлов (всегда так в Factorio), но остаётся молчаливым допущением; если Phase 3 когда-либо потребует нецелых координат курсора для тайлов, ключ придётся пересмотреть.
- **Dev-тулинг:** `busted`/`Lua 5.4`/`LuaRocks` установлены на машину разработчика (не в репозиторий) через WinGet — без прав администратора, поскольку изначально запрошенный Chocolatey-путь требовал elevation. Задокументировано здесь на случай переустановки/новой машины: `winget install DEVCOM.Lua`, затем `luarocks install --local busted` внутри окружения с MSVC (`vcvarsall.bat x64`) для компиляции C-частей (`luasystem`, `luafilesystem`, `lua-term`). Обёртки `busted`/`busted.bat`, делающие команду доступной из PowerShell и Git Bash без ручной настройки `LUA_PATH`/`LUA_CPATH` на каждый вызов, лежат в `%LOCALAPPDATA%\Microsoft\WinGet\Links\` (уже стабильно на `PATH` для обеих оболочек).
