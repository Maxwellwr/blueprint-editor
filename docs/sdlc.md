# Правила SDLC

Документ фиксирует процессные правила разработки мода `blueprint-editor`. Архитектурные решения по продукту — в [`docs/adr/`](adr/), живой статус фаз — в [`docs/roadmap.md`](roadmap.md). Это правила процесса, они меняются реже, чем сам мод, но не заморожены: любое устойчивое отклонение фиксируется правкой этого файла отдельным коммитом с обоснованием.

## Состав команды

Соло-разработка (разработчик + Claude Code). Правила ниже рассчитаны на это: нет отдельного ревьюера-человека, поэтому `/code-review` и ручной playtest — единственные страховочные шаги перед мержем.

## Git workflow

- **Ветка на фазу.** `phase-N-<slug>` от `main`, мержится в `main` только после прохождения Definition of Done фазы (см. ниже). `main` всегда в рабочем состоянии, соответствующем последней завершённой фазе.
- Внутри фазы дополнительные ветки не заводятся — фаза уже достаточно мелкая единица работы для соло-разработки (Phase 0–7, см. `docs/roadmap.md`).

## Коммиты

Conventional Commits на английском: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:` + краткое описание. Тело коммита (если нужно) может быть на русском.

## Code review

Обязателен перед каждым мержем ветки фазы в `main`: запуск `/code-review` на диффе ветки. Найденные проблемы фиксируются до мержа, а не переносятся в техдолг молча.

## Definition of Done фазы

Фаза считается завершённой и может быть смержена в `main`, только когда:

1. Пройден ручной playtest-чеклист фазы, зафиксированный в `docs/phases/phase-N-implementation.md`.
2. Пройден `/code-review`, найденные проблемы закрыты.
3. Документация обновлена: `docs/roadmap.md` (статус фазы), `docs/phases/phase-N-implementation.md` создан, ADR — если были архитектурные отклонения.
4. Для изменений схемы `storage` — добавлен шаг миграции в `scripts/migrations.lua` (см. ADR-0001, раздел 4).
5. `CHANGELOG.md` обновлён.
6. Для модулей без зависимости от Factorio API, затронутых фазой, — есть тесты, написанные по TDD (см. ниже), и они проходят.

Шаблоны для `phase-N-plan.md` / `phase-N-implementation.md` — в `docs/phases/TEMPLATE-*.md`.

## Версионирование

SemVer, `info.json.version`:

- `0.1.0` — по завершении Phase 0.
- Инкремент minor-версии на каждую следующую завершённую фазу (`0.2.0` после Phase 1, ..., `0.8.0` после Phase 7).
- `1.0.0` — только когда весь MVP (все фазы) пройден и мод считается стабильным для публикации на mod portal.
- Патч-версии (`0.1.1` и т.д.) — для фиксов внутри уже смерженной фазы, если такие понадобятся до старта следующей.

## Тестирование

Два разных режима верификации в зависимости от зависимости кода от Factorio API — подробное обоснование методов в ADR-0001, раздел 10.

**Чистая логика без зависимости от Factorio API** (`internal_id`/`entity_number` remap, фильтрация/сортировка каталога и подобное, принимающее и возвращающее обычные Lua-таблицы) — **обязательный TDD** через `busted`, начиная с той фазы, где такой код впервые появляется (в первую очередь Phase 2 для remap, Phase 5 для каталога): тест пишется до реализации, red-green-refactor. Это не факультативный stretch — часть Definition of Done фазы (пункт 6 выше).

**Код, зависящий от Factorio API** (всё, что трогает `storage` через игровые объекты, `LuaRendering`, GUI, события) — автотестами не покрывается (у Factorio-модов нет стандартного раннера для API-кода). Верификация:

- Dev-loop: символическая ссылка мода в `%APPDATA%\Factorio\mods\`, save-reload для `control.lua`/`scripts/*`, полный рестарт для `data.lua`.
- In-game debug-команда (`scripts/debug.lua`) — дамп состояния сессии через `serpent.block()`.
- Ground-truth cross-check экспортированного blueprint против вручную собранного в игре эталона.
- Real-paste validation — вставка экспортированного blueprint в реальный мир, движок как оракул корректности структуры.
- Обязательный ручной playtest-чеклист как основной метод верификации GUI/canvas-поведения (часть Definition of Done).

**Порядок ручного playtest'а с Claude Code.** Перед тем как передать playtest-чеклист фазы пользователю, во все обработчики, задействованные в чеклисте, добавляется временное диагностическое логирование под одним узнаваемым префиксом (например, `eb playtest:`) — так, чтобы по нему было легко grep'ать `factorio-current.log`. Пользователь прогоняет чеклист один раз (с обязательным dev-loop-рестартом, если фаза меняла `data.lua`/`data/*`) и отдаёт лог-файл вместо того, чтобы вручную описывать результат каждого шага. Claude Code разбирает лог и подтверждает по нему прохождение чеклиста (или выявляет расхождение и просит перепрогнать после фикса). Только после этого временное логирование убирается отдельным коммитом (`debug:`/`chore:` в духе «remove ... diagnostic logging») перед закрытием фазы (Задача «Закрытие фазы» в `phase-N-plan.md`, часть Definition of Done) — оно никогда не остаётся в `main`.

## Версия Factorio и проверка API-фактов

Разработка и playtest ведутся на Factorio **`2.0.77`** (stable-ветка, не experimental). При проверке любого факта Factorio Lua API (сигнатура функции, наличие свойства, поведение) — сверяться со **строго запиненной** версией документации: `https://lua-api.factorio.com/2.0.77/...` (или ближайшая по `major.minor`, если точного патча нет), никогда `https://lua-api.factorio.com/latest/`.

`/latest/` отслеживает experimental-ветку и может быть существенно впереди установленной версии. На практике это уже приводило к рабочему крашу мода в Phase 1: в момент проверки `/latest/` указывал на `2.1.17`, где у `LuaRecord` уже есть свойство `label`, которого нет в `2.0.77` — код, написанный по документации `/latest/`, упал в реальной игре с `LuaRecord doesn't contain key label`.

Точную установленную версию всегда можно подтвердить первой строкой `factorio-current.log` пользователя (например, `Factorio 2.0.77 (build ..., win64, steam, space-age)`) — сверяться с ней, а не полагаться на память/предположение.

## Архитектурные принципы

Часть уже зафиксирована как архитектурные решения в [ADR-0001](adr/0001-baseline-architecture.md) — здесь они перечислены как принципы, на которые code review должен ссылаться:

- **Инкапсуляция `storage`** — только через `state.lua`-accessors, никто другой не трогает `storage` напрямую (ADR-0001, раздел 4).
- **Preserve-unknown-fields** — импортированные сущности не пересобираются по хардкоду полей, непонятные/неиспользуемые модом поля переживают edit-сессию нетронутыми (ADR-0001, раздел 6).
- **Generic-каталог без хардкода имён** — перечисление сущностей/тайлов по `item.place_result`/`tile.items_to_place_this`, а не по спискам конкретных имён (ADR-0001, раздел 7).
- **`internal_id` вместо `entity_number`** — все внутренние ссылки (включая провода) по монотонному `internal_id`, `entity_number` — только на экспорте (ADR-0001, раздел 6).
- **Миграции только аддитивные** — поля `storage`/`Session`/`EntityRecord` только добавляются как nil-safe опциональные; переиспользование или удаление поля без миграции запрещено (ADR-0001, раздел 4).

Дополнительные принципы процесса и структуры кода:

### KISS + SOLID, адаптированные под data-oriented Lua

Мод — инструмент под конкретный API, а не общий фреймворк: не изобретаем самодельные ООП-обвязки, метатаблицы-классы или generic-plugin-системы там, где хватает обычных таблиц и функций (KISS). `canvas.lua` работает с `Session`/`EntityRecord` как с простыми Lua-таблицами, не объектами с методами.

SOLID переинтерпретирован для функциональных Lua-модулей (не классов):

- **S — Single Responsibility.** Граница ответственности каждого `scripts/*.lua`-файла задана раскладкой из ADR-0001 (раздел 3): `state.lua` — только storage-схема и accessors, `canvas.lua` — только мутации сессии, `rendering.lua` — только `LuaRendering`-обвязка, `blueprint_io.lua` — только импорт/экспорт, `catalog.lua` — только построение каталога. Если правка одной фичи требует правок в нескольких файлах по несвязанным причинам — граница ответственности проведена неверно, это сигнал к рефакторингу, а не к «ну ладно, один раз».
- **O — Open/Closed.** Уже реализовано generic-каталогом: добавление нового типа сущности любым другим модом не требует правки `catalog.lua`/`canvas.lua`, потому что перечисление идёт по `item.place_result`, а не по списку имён. Критерий для новой функциональности: «требует ли это редактирования существующего generic-кода под конкретный тип сущности?» — если да, дизайн нарушает OCP и стоит поискать более общее решение (обычно — через данные прототипа, а не через ветвление по имени/типу).
- **L — Liskov Substitution.** Мутации `canvas.lua` (place/remove/move/rotate) обязаны работать единообразно для любого `EntityRecord` вне зависимости от типа прототипа. Никакого `if entity.type == "..."` в общей логике мутаций — специфика конкретного типа (recipe, filters, grid) живёт только внутри `raw`-таблицы через preserve-unknown-fields, а не в ветвлении кода мутаций.
- **I — Interface Segregation.** Accessors в `state.lua` и мутации в `canvas.lua` — узкие функции под одну операцию (`state.get_session`, `canvas.place_entity`, `canvas.remove_entity`), а не одна God-функция с флагами-параметрами, переключающими поведение.
- **D — Dependency Inversion.** Модули верхнего уровня (`input.lua`, `palette_gui.lua`) зависят от мутационного API `canvas.lua`, а не напрямую от `storage` или сырых вызовов `LuaRendering` — то же правило инкапсуляции storage, распространённое на `canvas.lua` как единственную точку входа для мутаций сессии.

### Fail-fast для данных из Factorio API

Неожиданные данные из API (некорректные поля blueprint, отсутствующий prototype, битые ссылки на `entity_number` при импорте) обязаны громко упасть в лог (`error()`/явное сообщение игроку), а не тихо деградировать или молча пропускать сущность. Тихая деградация допустима только для явно опциональных/косметических путей (например, отсутствующая иконка предмета в палитре).

### Явный бюджет производительности

Каждый компонент, создающий render-объекты (`rendering.lua`) или потенциально большие структуры (`Session.entities`, `storage.catalog`), обязан иметь явный числовой лимит или порог предупреждения, зафиксированный в коде (константа с комментарием) или в `phase-N-implementation.md` — а не отложенную формулировку «проверим на Phase 7». Начальные цифры — грубая оценка на момент фазы, где компонент появляется, уточняется по факту playtest этой же фазы.
